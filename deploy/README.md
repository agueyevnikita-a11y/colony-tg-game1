# Закрытый стенд COLONY на российском VPS

Текущий сервер уже подключён к `https://colonygame.ru`. Для обычных обновлений приложения используйте [публикацию из GitHub](../docs/AUTODEPLOY.md): она сохраняет действующую базу и настройки доступа. Приведённые ниже команды относятся к первоначальной настройке, диагностике и отдельно проверяемому восстановлению сервера.

Эта конфигурация запускает существующую production-версию игры с новой PostgreSQL 16. Приложение слушает только `127.0.0.1:3000` сервера, PostgreSQL не публикует порт. Docker ограничивает журналы каждого контейнера тремя файлами по 10 МБ; оба сервиса перезапускаются после перезагрузки сервера.

Runtime использует отдельную роль `colony_app`, без административных прав и DDL. Схему и миграции выполняет сервис `db-tools` под владельцем `colony`; [подробности прав](DB_ROLES.md). Пароли администратора и приложения должны различаться.

Самостоятельный российский вход ещё не реализован: текущие API требуют подписанные данные Telegram. Открытие сайта через SSH-туннель позволяет проверить страницу и технические endpoints, но само по себе не позволяет войти в игру обычным браузером. `ALLOW_DEV_AUTH` остаётся `false`. Требования к самостоятельной версии описаны в [RUSSIA_WEB_REQUIREMENTS.md](../docs/RUSSIA_WEB_REQUIREMENTS.md).

Этот этап не меняет адрес бота, webhook, Railway, DNS и настройки платежей. Сервер пока не открывается для игроков. Не устанавливайте публичный reverse proxy и не запускайте команды `telegram:setup -- --apply`, `telegram:webhook -- --apply` или cron уведомлений на этом этапе.

## Подготовка

Нужны Ubuntu 24.04 LTS, Docker Engine с плагином Docker Compose, свободное место для сборки и резервных копий, доступ по SSH. В примерах checkout находится в `/opt/colony`. Не используйте рабочую папку с посторонними секретами или архивами БД: корневой Dockerfile копирует build context. `.env*` уже исключены корневым `.dockerignore`; архивы храните вне checkout.

Из каталога `deploy` на сервере:

```bash
cd /opt/colony/deploy
umask 077
cp .env.example .env
chmod 0600 .env
```

Заполните `.env` редактором на сервере. Не добавляйте секреты в Git, историю команд или сообщения. Все обязательные поля в примере пусты намеренно:

| Поле | Значение |
| --- | --- |
| `COLONY_DB_NAME` | По умолчанию `colony`; при смене используйте только строчные латинские буквы, цифры и `_`, начиная с буквы, до 63 символов |
| `POSTGRES_PASSWORD` | Отдельный случайный hex-пароль, чтобы не требовалось URL-кодирование |
| `APP_DB_PASSWORD` | Другой случайный hex-пароль: 64–256 символов, для роли приложения `colony_app` |
| `BOT_TOKEN` | Реальный токен принадлежащего владельцу проекта бота; не тестовая строка |
| `BOT_USERNAME`, `NEXT_PUBLIC_BOT_USERNAME` | Один и тот же username без `@`; публичная переменная встраивается при сборке |
| `APP_URL` | Планируемый настоящий HTTPS-origin без пути/query/fragment; до выбора адреса окончательная конфигурация не готова |
| `TELEGRAM_WEBHOOK_SECRET` | Отдельный случайный секрет 32–256 символов `A–Z a–z 0–9 _ -` |
| `CRON_SECRET` | Другой случайный секрет минимум 32 символа без пробелов |
| `ADMIN_TELEGRAM_IDS` | Числовые Telegram ID администраторов через запятую |
| `SUPPORT_URL` | Необязательная HTTPS-ссылка; можно оставить пустой |

`DATABASE_URL` Compose собирает из настроек PostgreSQL. `NODE_ENV=production`, `PORT=3000` и `ALLOW_DEV_AUTH=false` заданы в Compose. Не переносите Railway `PORT=8080` в этот запуск. Не используйте фиктивные Telegram-настройки ради успешного `/api/ready`.

Все команды ниже выполняются из `/opt/colony/deploy`; Compose автоматически читает лежащий рядом `.env`. Значения уже существующего окружения оболочки имеют приоритет над `.env`: используйте чистую SSH-сессию без старых экспортированных настроек. Проверка `config --quiet` не печатает развёрнутые секреты:

```bash
docker compose config --quiet
```

## Первый запуск с пустой базой

Существующие Docker volumes не удаляйте. Новая база создаётся только при первой инициализации пустого volume. Смена `POSTGRES_PASSWORD` в `.env` не меняет пароль внутри существующей БД. При выбранном сбросе прогресса старую базу Railway в этот volume не копируем.

```bash
docker compose up -d --wait db
docker compose build app
chmod 0644 provision-app-role.mjs
docker compose --profile tools run --rm --no-deps db-tools npm run db:init
docker compose --profile tools run --rm --no-deps db-tools
docker compose up -d --wait app
docker compose exec -T app npm run doctor -- --local
docker compose ps
curl --fail --silent --show-error http://127.0.0.1:3000/api/health/live
curl --fail --silent --show-error http://127.0.0.1:3000/api/health
curl --fail --silent --show-error http://127.0.0.1:3000/api/ready
```

`db:init` применяет накопительную схему `db/schema.sql` в транзакции. После этого отдельно запускать все старые миграции не нужно. Новая схема по умолчанию имеет `maintenance=false` и `beta_required=false`, поэтому закрытость стенда обеспечивают привязка к loopback и отсутствие публичного proxy, а не настройки игры.

`health/live` подтверждает работу процесса; `health` — соединение с БД; `ready` — настройки и необходимые таблицы/поля. Docker healthcheck использует только `health/live`. `doctor --local` не проверяет БД, Telegram и доставку webhook. Полный `doctor` до переключения webhook может сообщать о несовпадении адреса: не меняйте рабочий webhook только для устранения этого сообщения.

До выбора домена у частного стенда можно указать его действительный адрес туннеля `APP_URL=http://127.0.0.1:13000`. В этом случае `doctor --local` должен сообщить об отсутствии публичного HTTPS-origin, а `/api/ready` — вернуть HTTP 503 с `configuration=error`, даже если `database` и `schema` уже `ok`. Это незавершённая подготовка к публичному запуску; не подставляйте вымышленный HTTPS-адрес ради успешной проверки. Команды `curl --fail` для `ready` и `doctor` в таком режиме завершаются с ненулевым кодом ожидаемо.

Для просмотра страницы и проверок со своего компьютера оставьте открытым SSH-туннель, подставив пользователя и IP VPS:

```bash
ssh -N -L 127.0.0.1:13000:127.0.0.1:3000 USER@SERVER_IP
```

В локальном браузере откройте `http://127.0.0.1:13000`. Порт 3000 и порт БД не открывайте в firewall. Публичный запуск требует отдельного HTTPS reverse proxy и проверки самостоятельной авторизации, оплаты и документов перед подключением настоящих игроков.

## Резервная копия

Запускать от root, чтобы каталог и архивы принадлежали root:

```bash
cd /opt/colony/deploy
sudo bash ./backup.sh
```

Скрипт сохраняет consistent snapshot через `pg_dump` в custom-формате в `/var/backups/colony`, каталог `0700`, файлы `0600`. Пароль не передаётся в аргументах команды. Имя содержит UTC-время и случайный суффикс. Сначала создаётся `.partial`, после проверки списка архива — `.dump` и SHA-256. При ошибке неполный файл остаётся закрытым для других пользователей и не считается готовой копией. `pg_restore --list` проверяет чтение заголовка/оглавления, но не заменяет полное пробное восстановление.

Скрипт ничего не удаляет. Проверяйте свободное место и настройте хранение после оценки размера БД: например, семь ежедневных и четыре недельных подтверждённых копии. Решение об удалении старых копий принимайте отдельно после успешной проверки и копирования за пределы этого VPS. Локальный архив не защитит от потери VPS. Архив и `.env`/секреты нужно резервировать раздельно в защищённое российское хранилище; не помещайте их в Git или build context. Не меняйте `COMPOSE_PROJECT_NAME` или `COLONY_DB_NAME` в окружении root между запуском приложения и backup.

## Пробное восстановление без изменения рабочей базы

В root-сессии подставьте имя конкретного завершённого архива. Проверка создаёт отдельную БД, не останавливает приложение и ничего не удаляет:

```bash
cd /opt/colony/deploy
backup_file=/var/backups/colony/ИМЯ_ЗАВЕРШЕННОГО_АРХИВА.dump
cd /var/backups/colony
sha256sum --check "${backup_file}.sha256"
cd /opt/colony/deploy
restore_db="colony_restore_$(date -u +%Y%m%d_%H%M%S)"
docker compose exec -T db createdb --username=colony "$restore_db"
docker compose exec -T db pg_restore --username=colony --dbname="$restore_db" --exit-on-error --single-transaction --no-owner --no-acl < "$backup_file"
docker compose exec -T db psql --username=colony --dbname="$restore_db" --set=ON_ERROR_STOP=1 --command="SELECT current_database(), count(*) AS public_tables FROM information_schema.tables WHERE table_schema='public';"
```

Проверяйте также полноту схемы и ожидаемые счётчики/игровые состояния на тестовой копии, не выполняя действий покупки и отправки уведомлений. Тестовая БД останется на диске, её удаление в этот сценарий не входит. Учитывайте её размер при контроле свободного места.

## Восстановление рабочего приложения

Этот порядок предназначен для отдельно согласованного восстановления, а не первого запуска:

1. Остановите `app` командой `docker compose stop app`, чтобы прекратить записи. Если текущая БД доступна, сделайте её контрольный backup до переключения.
2. Проверьте SHA-256 нужного архива и восстановите его в **новую** БД по предыдущему разделу. Запишите её имя и проверьте результат. Старую БД сохраните.
3. В защищённом `.env` замените `COLONY_DB_NAME` на имя проверенной восстановленной БД. Сохраните тот же пароль/пользователя и volume. При существующем volume PostgreSQL не создаст новую БД только из-за изменения `.env`, поэтому пункт 2 обязателен.
4. Выполните `docker compose up -d --wait db`, затем `docker compose up -d --wait app`. Пересоздание контейнера `db` с прежним volume обновит `POSTGRES_DB`, используемый проверками и backup; данные всех БД сохранятся.
5. До запуска приложения подготовьте роль в восстановленной БД: `docker compose --profile tools run --rm --no-deps db-tools`. Если архив старее кода, перед этой командой примените `docker compose --profile tools run --rm --no-deps db-tools npm run db:init`. Проверьте все три endpoint и ожидаемое состояние игры, затем только возобновляйте внешний доступ.

Откат до новых записей: остановить `app`, вернуть старое имя `COLONY_DB_NAME` и повторить запуск/проверки с тем же volume. Не выполняйте `docker compose down -v`, `DROP DATABASE` или удаление файлов PostgreSQL для этого порядка.

## Подготовленный HTTPS для colonygame.ru

`https.compose.yml` добавляет Caddy 2.11.9 с постоянными томами сертификатов и ограниченными журналами. `Caddyfile` принимает имя `colonygame.ru`; публикация по IP владельцем отклонена. До регистрации домена и появления правильной делегации в .RU публичный proxy не запускать. DNS A должен указывать на `195.58.54.93`, без AAAA на посторонний сервер. После выпуска сертификата проверять `curl https://colonygame.ru/api/ready` без отключения проверки TLS.

После согласованного подключения HTTPS использовать `docker compose -f compose.yml -f https.compose.yml ...` при обновлении контейнеров. Смена `APP_URL` на `https://colonygame.ru` требует пересоздания `app`. `telegram:setup -- --apply` переключает меню и webhook; Main Mini App из профиля/startapp меняется отдельно в BotFather. Нельзя объявлять Telegram-перенос завершённым только по успешному `getChatMenuButton`.

Команды бота возвращают `sendMessage` прямо в JSON-ответе на аутентифицированный webhook — это поддерживаемый Telegram способ ответа без отдельного исходящего запроса. Он требует доставки входящего webhook, а результат отправки сообщения в этом режиме недоступен приложению. Покупки и уведомления по-прежнему требуют работоспособного исходящего соединения с Telegram API. При диагностике проверять отдельно доступность сайта, реальный запуск Main Mini App, доставку команд и исходящий API; успешный `/api/ready` и `doctor --local` не доказывают работу Telegram-сети.
