# Публикация COLONY на RUVDS из GitHub

Этот порядок обновляет только приложение `colony-russia/app`. PostgreSQL, его volume, секреты, Caddy, webhook, игровые данные и настройки закрытого режима не заменяются. Выпуск не запускает миграции, уведомления, синтетические игровые сессии или покупки.

## Как проходит обновление

1. Push в `main` запускает существующий `CI`: типы, тесты, повторное применение схемы в отдельной `colony_ci`, production-сборку и проверку образа.
2. `Deploy COLONY to RUVDS` запускается после успешного **push/main CI именно этого репозитория**. Проверки PR и fork не получают доступ к публикации. Выпуски сериализованы; отмена работающего обновления не используется.
3. Workflow проверяет SHA текущего `main`, затем передаёт серверу только `deploy <полный SHA> <ID успешного CI>`. Устаревший commit пропускается. Проверка повторяется сервером независимо от workflow, включая путь `.github/workflows/ci.yml`.
4. Сервер скачивает исходники публичного репозитория по точному SHA. Архив проверяется на выход из каталога, ссылки, специальные файлы, секретные/generated-каталоги и размер. `.env` остаётся вне исходников и подключается из `/opt/colony/shared/.env`.
5. Новый образ собирается до переключения работающего приложения. Отдельный кандидат слушает только `127.0.0.1:3301`; проверяются `health/live`, `health`, `ready` и точная версия. Игровые маршруты не вызываются.
6. Создаётся backup PostgreSQL; сохраняются прежний image и каталог. Новый `app` запускается с `--no-deps`, без пересоздания БД или Caddy. Проверяются версия, readiness, прежние контейнер и volume БД. Сверяются `maintenance`/`beta_required` из `system_settings`, все переключатели и проценты раскатки из `feature_flags`, а также все персональные `feature_flag_overrides`. Количество пользователей, покупок и альянсов не должно уменьшаться.
7. После успеха атомарно меняется `/opt/colony/current`. При ошибке активации восстанавливается прежнее приложение; **база из backup автоматически не восстанавливается**, чтобы не потерять новые записи.

Успех workflow подтверждает публичную версию сайта. Реальное открытие Mini App и доставка команд Telegram остаются отдельной пользовательской проверкой.

## Однократная настройка сервера

Выполняет оператор с уже имеющимся доверенным SSH-доступом. Сначала объединяются и проверяются серверные исправления с новым игровым кодом. Скрипты устанавливаются из просмотренной копии; **скачанный release никогда не заменяет исполняемый updater автоматически**.

```bash
install -d -o root -g root -m 0755 /usr/local/lib/colony
install -o root -g root -m 0755 deploy/release.sh /usr/local/lib/colony/release.sh
install -o root -g root -m 0755 deploy/ssh-deploy-command.sh /usr/local/sbin/colony-deploy
```

Нужны `python3`, `curl`, `flock`, Docker/Compose, существующие `/opt/colony/releases`, `/opt/colony/current` и root-owned `/opt/colony/shared/.env` с правами `0600`. Сохранённый ключ SSH-сервера проверяется до настройки. У сервера должен быть исходящий HTTPS к `api.github.com` и `codeload.github.com`. Приватный GitHub-токен на VPS не требуется.

Создаётся отдельный пользователь `colony-deploy`: без пароля и без группы `docker`. Нужна обычная оболочка `/bin/bash` или `/bin/sh`: `nologin` не выполнит даже обязательную SSH-команду. Его домашний каталог, `.ssh`, `authorized_keys` и любые файлы запуска оболочки должны принадлежать root, не быть доступны для изменения этим пользователем. Нельзя давать этому пользователю общий `sudo`, Docker socket или свободную оболочку через ключ Actions.

В отдельном root-owned sudoers-файле, проверенном `visudo --check --file ...`:

```sudoers
colony-deploy ALL=(root) NOPASSWD: /usr/local/sbin/colony-deploy
```

В `authorized_keys` — один отдельный ключ публикации с обязательной командой (публичный ключ подставляется оператором):

```text
restrict,command="/usr/bin/sudo -n /usr/local/sbin/colony-deploy \"$SSH_ORIGINAL_COMMAND\"" ssh-ed25519 PUBLIC_KEY COLONY-GitHub-deploy
```

Wrapper принимает ровно один аргумент, проверяет всю строку по строгому шаблону и вызывает только установленный updater. Переадресация, PTY, агент и произвольные команды для этого ключа запрещены. Другие существующие SSH-ключи оператора не меняются.

## GitHub

В environment `production` создать secrets:

| Secret | Назначение |
| --- | --- |
| `COLONY_DEPLOY_HOST` | Текущий IP/hostname RUVDS |
| `COLONY_DEPLOY_USER` | `colony-deploy` |
| `COLONY_DEPLOY_KEY` | Приватная часть отдельного ключа публикации |
| `COLONY_DEPLOY_KNOWN_HOSTS` | Проверенная строка `known_hosts` сервера |

Ограничить environment `production` веткой `main`. Публичный ключ SSH-сервера получить по уже проверенному административному соединению; `ssh-keyscan` без сверки не использовать как установление доверия. Ключ публикации и остальные значения не выводить в чаты/логи и не коммитить. GitHub Actions использует строгую проверку host key и не сохраняет ключ в артефактах.

Самый первый объединённый выпуск можно запустить вручную от root после успешного CI:

```bash
/usr/local/lib/colony/release.sh FULL_COMMIT_SHA CI_RUN_ID
```

Workflow также допускает ручной запуск на `main` с `ci_run_id`, но только для текущего `main` и его успешного push-CI. Ручной запуск не позволяет передать другую ветку, непроверенный SHA или команду shell.

## Изменения, которые требуют оператора

Автопубликация откажется продолжать, если по сравнению с работающим release изменились схема, Dockerfile, Compose/Caddy, разделение ролей БД, backup или уже присутствовавшие скрипты управления публикацией. Это защищает от случайного обновления инфраструктуры и неподготовленных миграций. Для таких изменений нужен отдельный просмотр, резервная копия и проверенный ручной порядок; updater сам не применяет `db:init` к production.

Старые каталоги, образы, исходные архивы, диагностика и backup сохраняются. Доступ к диагностике в `/opt/colony/shared/release-check-*` закрыт; файлы состояния не содержат токенов или паролей, но снимок индивидуальных переключателей содержит внутренние UUID пользователей и не предназначен для публикации. При одновременном намеренном удалении аккаунта или альянса проверка количества записей может остановить выпуск: оператор сначала проверяет причину уменьшения. Неполный каталог без `.colony-release-sha` требует ручной проверки, а не автоматического удаления/перезаписи. Нужны контроль свободного места и отдельная политика хранения проверенных копий.

При аварии: проверить workflow, серверный вывод updater, `/api/health/live` и `/api/ready`. Не запускать `docker compose down -v`, очистку volume, `DROP DATABASE`, удаление старых выпусков или смену секретов ради повторной публикации.
