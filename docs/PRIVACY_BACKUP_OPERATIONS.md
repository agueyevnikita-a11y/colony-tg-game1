# COLONY: удаление данных из копий и безопасное восстановление

Рабочий порядок от 11 ноября 2026 года. Настройка механизма не является разрешением уничтожить существующие данные игроков или архивы. Владелец сообщил, что дополнительных сделанных им копий нет; серверные, локальные, восстановленные и провайдерские копии всё равно проверяются отдельно. Старое хранилище Railway остаётся самостоятельным незавершённым пунктом.

## Границы инструментов

`scripts/privacy-copy-inventory.mjs` составляет каталог метаданных, ничего не удаляет и не восстанавливает. CLI принимает только один заранее разрешённый каталог: `/var/backups/colony` на Linux или `D:/colony/.local-data/migration` на Windows. `--root` не позволяет читать произвольную другую папку.

Сканируется один уровень; учитываются обычные файлы с окончаниями `.dump`, `.dump.partial`, `.sha256`. Папки внутри не обходятся. Ссылки, junctions, нештатные типы файлов, hard links и замеченные изменения во время чтения отклоняются. Файлы читаются потоком только для SHA-256: дампы не разбираются, содержимое файлов и секреты не выводятся. `.sha256` в каталоге — самостоятельный артефакт; его хеш не означает проверки записанной внутри контрольной суммы или пригодности дампа к восстановлению.

Результат JSON содержит `revision: 1`, разрешённый `root`, время формирования UTC и `artifacts`: абсолютный `path`, размер `size`, `sha256`, время изменения UTC `modifiedAt`, тип `kind` (`dump`, `partial`, `checksum`). Это снимок для подготовки решения, а не готовая команда уничтожения. Перед исполнением план повторно сверяется под блокировкой; изменение файла, хеша или состава копий требует нового плана.

На сервере с установленным Node.js:

```bash
node scripts/privacy-copy-inventory.mjs --root /var/backups/colony
```

Для текущего VPS наличие Node.js на хосте не предполагается. После проверенного выпуска, в образ которого включён CLI, можно использовать установленный Docker с образом работающего приложения. Ему предоставляется только read-only каталог архивов, без сети и серверного `.env`:

```bash
image="$(docker inspect --format '{{.Image}}' colony-russia-app-1)"
docker run --rm --read-only --network none --user 0:0 \
  --mount type=bind,source=/var/backups/colony,target=/var/backups/colony,readonly \
  "$image" node scripts/privacy-copy-inventory.mjs --root /var/backups/colony
```

До такого выпуска оператор использует отдельно просмотренную копию скрипта; старый образ не следует считать содержащим новый инструмент. Не монтировать для этой задачи весь `shared`, секреты или каталог PostgreSQL.

На компьютере владельца, из `D:\colony`:

```powershell
node scripts/privacy-copy-inventory.mjs --root D:/colony/.local-data/migration
```

JSON и последующие планы хранить в защищённом рабочем каталоге вне Git и чата. Имена файлов и служебные идентификаторы тоже не следует публиковать без необходимости. `ROOT_CHANGED` или `ARTIFACT_CHANGED` означает, что нужно дождаться окончания резервирования и повторить только инвентаризацию; частичный результат нельзя считать согласованным планом.

## Порядок выполнения

1. Принять обращение, проверить принадлежность аккаунта и полномочия заявителя. Код подтверждения связывает обращение с аккаунтом, но не заменяет разбор содержания требования. Зафиксировать применимые сроки и основания сохранения необходимых отдельных сведений.
2. Подготовить предварительный план без уничтожения. Включить основную БД, связанные записи, журналы и контексты, серверные `.dump` и `.partial`, локальные выгрузки, ранее восстановленные БД, диагностические JSON, почту, провайдерские snapshots и прежнее размещение Railway. UUID новой игры может отличаться от UUID прежнего размещения.
3. Для реальных данных подготовить конкретное подтверждаемое действие: аккаунт, категории, сохраняемые исключения, полный список затронутых файлов/БД, контрольные суммы, последствия для восстановления и способ подтверждения исполнения. Получить отдельное согласие на фактическое необратимое действие после просмотра этого результата. Согласованные для черновика политики 7 дней сами по себе не разрешают удалить старые архивы.
4. Исполнить проверенное удаление активных данных и записать минимальное событие в защищённый журнал вне восстанавливаемого PostgreSQL. Для проекта предусмотрен отдельный каталог `/opt/colony/shared/privacy`, подключаемый приложению как `/app/privacy`; к частным файлам исполнителя приложения доступ не получают. Конкретные права и раздельные подкаталоги проверяются перед включением исполнения.
5. Создать свежую чистую резервную копию после применения всех удалений. Проверить SHA-256, затем действительно восстановить её в отдельную закрытую БД, повторить журнал удалений и проверить отсутствие данных выбранного игрока и сохранность остальных. Чтения оглавления `pg_restore --list` для этого недостаточно.
6. Подготовить замену или вывод прежних общих архивов. Для сохранения исторических точек восстановления: каждый затронутый архив восстановить в изолированной среде, применить удаления, сформировать новую копию и проверить её восстановление. Другой вариант — заменить старые точки одной свежей копией; потерю прежней истории для остальных игроков отдельно показать владельцу.
7. Уничтожить или вывести конкретные старые копии только по согласованному перечню и предусмотренному законному порядку. Пока оригинал, quarantine-копия или восстановленная БД сохраняется, не заявлять полное уничтожение. Учесть временные файлы очистки и новые копии самого журнала; оформить фактические результаты и требуемые доказательства.
8. Отдельно установить исполнение у RUVDS и Railway. Отсутствие публичного порта, статус offline или удаление записи из списка файлов не подтверждают отсутствия провайдерских снимков и иных копий. Согласовать их состав, доступ, сроки и подтверждение с провайдером, не запуская старые платные ресурсы ради такой проверки автоматически.

## Блокировки и повторное восстановление

`deploy/backup.sh` получает эксклюзивную блокировку `/var/lock/colony-data.lock` через FD 8 до `pg_dump` и держит её до окончания контрольной суммы. Запускаемый отдельно ежедневный backup получает только эту блокировку. Исполнитель удаления получает сначала `/var/lock/colony-release.lock` (FD 9), затем `colony-data.lock` (FD 8). Вложенный запуск `backup.sh` из процесса, уже удерживающего data lock, недопустим: чистую копию исполнитель создаёт в своей проверенной последовательности.

Это важно для гонки snapshot: архив может начаться до удаления, а получить окончательное имя после него. Его чистоту определяют согласованная последовательность и поколение журнала, а не только имя или `mtime`. Блокировка также должна охватывать восстановление; проверка неизменности файлов в inventory не заменяет её.

Порядок восстановления закрыт для обычного игрового доступа до выполнения всех шагов:

1. Получить актуальный защищённый журнал независимо от восстанавливаемого дампа.
2. Восстановить данные только в изолированную БД; применить все удаления после поколения snapshot и отозвать сохранённые активные коды подтверждения аккаунта.
3. Проверить поколение журнала и минимальную поддерживаемую privacy-capability приложения. Не включать старый образ, который не проверяет закрытие аккаунта и может снова создать профиль.
4. Проверить отсутствие удалённых сведений, необходимые оставшиеся категории и сохранность других игроков. Только после этого разрешать предусмотренную активацию.

Новый журнал не следует хранить единственной копией внутри того же PGdump: восстановление откатит одновременно данные и отметку об их удалении. Нужны отдельные защищённые копии журнала и проверяемый порядок их восстановления. Срок и основание хранения его доказательств оформляются отдельно; он не должен содержать весь уничтожаемый профиль.

## Существующие копии и ограничения выпуска

На 11 ноября read-only инвентаризация `/var/backups/colony` нашла 15 `.dump` и 15 `.sha256`, без `.partial`. Содержимое архивов при этой инвентаризации не восстанавливалось. Защищённый manifest хранится вне Git; при реальном исполнении нужен новый снимок под блокировкой. Никакой архив в рамках подготовки не уничтожен.

Известны локальные `colony-20261108T182121Z-QADEXH.dump`, `colony-20261108T195001Z-T06VGQ.dump` и три оставленные серверные БД: `colony_restore_20261108` (0 пользователей), `colony_restore_20261108_post_cutover` (1), `colony_restore_release_20261110_133230` (2). Числа отражают отдельную проверку таблицы users, а не отсутствие других персональных сведений. Рабочая база содержит 2 пользователей; ни одного из них подготовка механизма не удаляет. Успешный автодеплой создаёт дополнительные серверные архивы; свежий каталог обязателен.

`release-check-*` и `ownership-check-*` в серверном `shared` могут содержать диагностические снимки `feature_flag_overrides` с UUID пользователей. Их учитывать отдельно. Весь `shared`, старые release-каталоги и Docker volumes не удалять ради очистки отдельного аккаунта.

Изменения схемы, backup-скрипта и управляющего updater блокируются обычным автодеплоем. Первый выпуск требует отдельно проверенной ручной последовательности. Установленный root-owned updater не заменяется автоматически файлом из GitHub. Перед первым реальным удалением проверить privacy-floor и согласование worker с проверкой уменьшения счётчиков пользователей при публикации. См. [порядок публикации](AUTODEPLOY.md).

Этот порядок не включает автоматическое удаление старых архивов. Неподтверждённые копии, остатки Railway, провайдерские snapshots, почта и сроки удаления из старых резервных носителей остаются открытыми до фактической проверки и исполнения. Стирание обычного файла не следует выдавать за подтверждённое физическое уничтожение всех копий на SSD и у провайдера.
